# Aeryvex AI Game Factory architecture and validation

Factory implementation lives in ai_factory/. Existing original_game/, scripts/, references, canon, rulers, progression and assets are protected user work: do not replace them with generated output. Factory projects default to factory_projects/ and must not target existing repository content. Preserve Orion's staff/dual swords, Thalen's dual swords, lightning hierarchy, ten forbidden Void trials and Supreme Grand Master progression. Follow original_game/character_visual_lock.json; no appearance changes or image/model substitutions without explicit approval.

Architecture: CLI -> validated provider proposal -> persistent versioned Game Bible -> dependency task graph -> deterministic Godot template -> real engine QA -> integrity manifest/project archive. Providers cannot execute commands or emit arbitrary executable code. Source edits are detected before regeneration. Revisions preserve history, lock snapshots and checkpoints; never silently restart an existing project. Unsupported prompt clauses stay pending, never implemented by labels alone.

Use python3 -m unittest discover -s ai_factory/tests -v. Godot validation requires Godot4.2+ via GODOT_BIN or PATH, writable isolated XDG paths, import/startup/scenario runs, explicit success marker and zero engine errors. Python checks alone do not certify Godot. Logs bind to source/config hashes and revision. Exported project ZIP is not an OS executable. No automatic deployment or merge. No credentials in source; hosted providers require explicit configuration and environment credentials. Missing GPU/assets/tools are BLOCKED, not fake successes. All artwork in the initial template is primitive prototype drawing, not final assets.

Preserve checkpoints/config in Git/durable storage: Kaggle /kaggle/working alone is ephemeral. Commit source and project bibles/checkpoints deliberately; engine caches/log caches/binary builds must not be committed. Do not write generated files into approved source folders. Check hashes before accepting evidence or overwriting managed code. Tests should exercise actual generated gameplay, revisions, errors and persistence.
